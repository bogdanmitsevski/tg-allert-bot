# Job Matcher: опис і план реалізації

## Проблема

Вакансії для українського IT-ринку розкидані по DOU, Djinni і Work.ua. Щоб знайти підходящі, треба щодня переглядати три сайти й вручну порівнювати кожну вакансію зі своїм досвідом. Якщо в людини кілька резюме під різні ролі, наприклад backend і fullstack, роботи стає ще більше.

## Рішення

Бекенд на NestJS із Fastify, у який користувач завантажує одне або кілька резюме. Модель Gemini розбирає кожне резюме на структурований профіль: навички, ролі, роки досвіду, рівень. Сервіс регулярно збирає вакансії з DOU, Djinni і Work.ua та для обраних користувачем резюме повертає лише ті вакансії, де відповідність становить 70% і більше.

Користувач сам обирає, за якими резюме шукати, і може задати діапазон років досвіду, який його цікавить. Фронтенду в першій версії немає: роботу з API забезпечує Swagger.

## Основні сценарії

1. Користувач реєструється й входить, отримуючи пару токенів: access і refresh.
2. Завантажує резюме у форматі PDF або DOCX. Файл зберігається в S3, а Gemini у фоні розбирає його на профіль.
3. Переглядає свої резюме та їхні статуси розбору, за потреби видаляє резюме або запускає розбір повторно.
4. Запускає пошук: обирає одне або кілька резюме, а також, за бажанням, діапазон років досвіду й джерела.
5. Отримує список вакансій із відповідністю від 70%, відсортований за оцінкою. Для кожної вакансії видно, яке резюме підійшло найкраще і чому.

## Архітектура

Сервіс складається з трьох незалежних потоків.

```text
Завантаження резюме
  → перевірка типу й розміру файлу
  → файл зберігається в приватному S3-бакеті
  → запис у БД зі статусом PENDING
  → фоновий розбір через Gemini → профіль резюме, статус PARSED або FAILED

Збір вакансій (за розкладом, незалежно від пошуків)
  → адаптер кожного джерела: DOU (RSS), Djinni (RSS), Work.ua (HTML)
  → нормалізація: навички, вимоги до досвіду, рівень
  → збереження в БД без дублів за парою (source, externalId)

Пошук
  → POST /searches з обраними резюме й параметрами → статус PENDING
  → фільтр за свіжістю, джерелами й роками досвіду
  → попередній відбір без LLM за збігом навичок
  → оцінка Gemini для пари (резюме, вакансія) → кеш оцінок
  → результати з оцінкою ≥ 70, статус DONE
```

Вакансії збираються за розкладом, а не під час кожного пошуку. Так пошук не залежить від швидкості й доступності сайтів, а самі сайти не отримують запит на кожен пошук користувача.

Пошук і розбір резюме виконуються асинхронно, бо виклики Gemini тривають секунди. API одразу повертає id задачі, а клієнт перевіряє її статус.

## Як рахується відповідність

Оцінка є цілим числом від 0 до 100 і рахується для кожної пари «резюме — вакансія».

1. **Жорсткі фільтри** відсіюють вакансію без виклику моделі:
   - вакансія старша за `VACANCY_MAX_AGE_DAYS` (за замовчуванням 30 днів);
   - джерело не входить у вибрані;
   - діапазон досвіду з вакансії не перетинається з діапазоном, який задав користувач.
2. **Попередній відбір** працює без LLM. Вакансії сортуються за часткою навичок вакансії, які є в резюме. Далі йдуть лише `MATCH_PREFILTER_LIMIT` найкращих вакансій на резюме (за замовчуванням 50), щоб обмежити кількість і вартість викликів Gemini.
3. **Оцінка Gemini** за фіксованою шкалою з `temperature: 0`:

| Складова | Вага |
| --- | --- |
| Збіг ключових навичок і технологій | 50 |
| Відповідність досвіду вимогам вакансії | 20 |
| Відповідність ролі й рівня (Junior, Middle, Senior) | 20 |
| Інше: мова, формат роботи, домен | 10 |

Модель повертає JSON із загальною оцінкою, оцінками за складовими, коротким поясненням і списком навичок, яких бракує. Сервіс перевіряє відповідь за схемою, а підсумкову оцінку перераховує сам як суму складових, не покладаючись на число від моделі.

Вакансія потрапляє в результати, якщо її оцінка хоча б для одного з обраних резюме дорівнює або перевищує `MATCH_THRESHOLD` (за замовчуванням 70). Оцінки кешуються за ключем `(cvId, версія профілю, vacancyId, хеш тексту вакансії)`, тому повторний пошук не викликає модель повторно.

**Роки досвіду.** Параметр `experience` задає діапазон `{ min, max }` у роках, обидва поля необов'язкові. Вакансія проходить фільтр, якщо її вимоги перетинаються з цим діапазоном. Якщо параметр не задано, фільтр не застосовується, але досвід усе одно враховується в оцінці. Вакансії, де вимоги до досвіду визначити не вдалося, не відкидаються: вони позначаються прапорцем `experienceUnknown`.

## Модель даних

| Таблиця | Призначення й основні поля |
| --- | --- |
| `users` | `id`, `email` (унікальний, у нижньому регістрі), `passwordHash`, `createdAt` |
| `refresh_tokens` | `id`, `userId`, `tokenHash`, `expiresAt`, `revokedAt`, `replacedById` |
| `cvs` | `id`, `userId`, `title`, `originalFileName`, `mimeType`, `sizeBytes`, `s3Key`, `parseStatus`, `parseError`, `profile` (jsonb), `profileVersion`, `createdAt` |
| `vacancies` | `id`, `source`, `externalId`, `url`, `title`, `company`, `location`, `remote`, `description`, `skills`, `experienceMin`, `experienceMax`, `seniority`, `contentHash`, `publishedAt`, `fetchedAt` |
| `searches` | `id`, `userId`, `status`, `experienceMin`, `experienceMax`, `sources`, `error`, `createdAt`, `finishedAt` |
| `search_cvs` | `searchId`, `cvId`: обрані для пошуку резюме |
| `match_scores` | `cvId`, `profileVersion`, `vacancyId`, `contentHash`, `score`, `breakdown` (jsonb), `reasons`, `missingSkills`: кеш оцінок |
| `search_results` | `searchId`, `vacancyId`, `bestCvId`, `bestScore` |

Схема змінюється лише через міграції TypeORM, `synchronize` вимкнено в усіх середовищах. Видалення користувача чи резюме каскадно видаляє пов'язані записи й файл у S3.

## API

Усі маршрути, крім реєстрації, входу й оновлення токена, вимагають заголовок `Authorization: Bearer <access token>`. Документація Swagger доступна за адресою `/api/docs`.

| Метод і шлях | Призначення |
| --- | --- |
| `POST /auth/register` | Реєстрація за email і паролем |
| `POST /auth/login` | Вхід, повертає access і refresh токени |
| `POST /auth/refresh` | Нова пара токенів, старий refresh токен відкликається |
| `POST /auth/logout` | Відкликання refresh токена |
| `GET /auth/me` | Поточний користувач |
| `POST /cvs` | Завантаження резюме (`multipart/form-data`) |
| `GET /cvs` | Список резюме користувача зі статусами розбору |
| `GET /cvs/:id` | Резюме з розібраним профілем |
| `GET /cvs/:id/download` | Тимчасове посилання на файл у S3 |
| `POST /cvs/:id/reparse` | Повторний розбір |
| `DELETE /cvs/:id` | Видалення резюме та файлу |
| `POST /searches` | Запуск пошуку: `cvIds`, `experience?`, `sources?` |
| `GET /searches` | Історія пошуків |
| `GET /searches/:id` | Статус пошуку |
| `GET /searches/:id/results` | Вакансії з оцінкою від 70% з пагінацією |

Користувач бачить і змінює лише власні резюме та пошуки. Чужий `id` повертає `404`, а не `403`, щоб не розкривати існування запису.

## Стек

- **Основа:** NestJS 12 з Fastify (`@nestjs/platform-fastify`, вже в репозиторії), `@nestjs/config`, `class-validator`, `class-transformer`. Бібліотеки лише для Express, як-от `multer` чи `helmet`, не підходять: замість них використовуються плагіни Fastify.
- **БД:** PostgreSQL, `typeorm`, `@nestjs/typeorm`, `pg`.
- **Авторизація:** `@nestjs/jwt`, `@nestjs/passport`, `argon2` для хешування паролів, `@nestjs/throttler` для обмеження спроб входу.
- **Документація:** `@nestjs/swagger` і `@fastify/static`, без якого Swagger UI не працює на Fastify.
- **Файли:** `@fastify/multipart` для приймання файлів, `@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`.
- **Безпека HTTP:** `@fastify/helmet` для заголовків безпеки.
- **LLM:** `@google/genai` для розбору резюме й оцінки відповідності.
- **Вакансії:** `cheerio` для HTML, парсер RSS, `@nestjs/schedule` для запуску за розкладом.
- **Документи:** `mammoth` для витягування тексту з DOCX.
- **Локальна розробка:** Docker Compose з PostgreSQL і MinIO як S3-сумісним сховищем.

Перед використанням кожної бібліотеки треба звірити її поточне API через Context7, бо пакети часто змінюються.

## Покроковий план

Критерії кожного кроку поділені на два типи. **Автоматично** перевіряють агенти за допомогою тестів і моків. **Вручну** перевіряє користувач на реальних сервісах (AWS, Gemini, сайти вакансій), бо агенти не мають доступу до файлу `.env` і зовнішньої мережі. Крок завершено, коли виконано обидва типи критеріїв.

Тести не звертаються до реальних S3, Gemini й сайтів вакансій: ці залежності підміняються через DI Nest. Для інтеграційних і e2e-тестів потрібна тестова база PostgreSQL з Docker Compose, яку користувач запускає командою `docker compose up -d`. E2e-тести створюють застосунок із `FastifyAdapter` і надсилають запити через `app.inject()`, без запуску сервера.

### Крок 1. Основа проєкту

1. Користувач: створити AWS-акаунт, приватний S3-бакет і IAM-користувача з доступом лише до цього бакета, а також отримати ключ Gemini API.
2. Додати `docker-compose.yml` із PostgreSQL (основна й тестова бази) та MinIO.
3. Створити `.env.example` зі змінними `PORT`, `DATABASE_URL`, `DATABASE_URL_TEST`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `AWS_REGION`, `S3_BUCKET`, `S3_ENDPOINT` (для MinIO), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `MATCH_THRESHOLD`, `SWAGGER_ENABLED`.
4. Підключити `@nestjs/config` із перевіркою змінних під час запуску.
5. Підключити TypeORM із міграціями та командами `migration:generate`, `migration:run` і `migration:revert`.
6. Увімкнути глобальний `ValidationPipe` з `whitelist` і `forbidNonWhitelisted`.
7. Підключити Swagger на `/api/docs` з bearer-авторизацією та плагіном `@nestjs/swagger` у `nest-cli.json`. Для Fastify потрібен пакет `@fastify/static`. Swagger вмикається змінною `SWAGGER_ENABLED`.
8. Підключити `@fastify/helmet`. Політика CSP має дозволяти ресурси Swagger UI, інакше сторінка документації не відкриється.
9. Прибрати стартові `AppController` і `AppService`, а порт брати зі змінної `PORT`.

**Готово, коли (автоматично):** застосунок не стартує без потрібних змінних і пояснює, якої бракує. Міграції застосовуються до тестової бази. Тест перевіряє, що `/api/docs-json` віддає документ OpenAPI.

**Готово, коли (вручну):** після `docker compose up -d` і заповнення `.env` застосунок стартує, а Swagger відкривається в браузері.

### Крок 2. Реєстрація й авторизація

1. Створити сутності `User` і `RefreshToken` та міграцію для них.
2. Додати реєстрацію: email нормалізується до нижнього регістру, пароль має щонайменше 8 символів і хешується через `argon2`. Повторний email повертає `409`.
3. Додати вхід: access токен живе 15 хвилин, refresh токен 30 днів. У БД зберігається лише хеш refresh токена.
4. Під час оновлення старий refresh токен відкликається, а видається нова пара. Повторне використання відкликаного токена відкликає всі токени користувача, бо це ознака викрадення.
5. Додати `logout`, `GET /auth/me` і guard, який за замовчуванням захищає всі маршрути, а відкриті маршрути позначаються декоратором `@Public()`.
6. Обмежити кількість спроб входу й реєстрації через `@nestjs/throttler`.
7. Описати DTO й відповіді в Swagger.

**Важливо:** паролі, хеші й токени не логуються та не повертаються у відповідях.

**Готово, коли (автоматично):** e2e-тести покривають реєстрацію, повторний email, вхід із правильним і хибним паролем, доступ із токеном і без нього, ротацію refresh токена, повторне використання відкликаного токена, logout і обмеження кількості спроб.

**Готово, коли (вручну):** користувач проходить реєстрацію, вхід і виклик захищеного маршруту через Swagger.

### Крок 3. Завантаження резюме в S3

1. Створити сутність `Cv` і міграцію.
2. Створити `StorageService` поверх `@aws-sdk/client-s3`, який підтримує і AWS, і MinIO через `S3_ENDPOINT` і `forcePathStyle`.
3. Приймати PDF і DOCX розміром до 5 МБ через `FileInterceptor` з `@nestjs/platform-fastify/multipart`, який працює поверх `@fastify/multipart`. Ліміт розміру задавати і в інтерцепторі, щоб завеликий файл відхилявся ще під час приймання. Тип визначати за вмістом файлу, а не лише за розширенням чи заголовком `Content-Type`.
4. Зберігати файл під ключем `cvs/<userId>/<cvId>.<ext>`, а оригінальну назву файлу тримати лише в БД. Бакет приватний, з шифруванням на боці сервера.
5. Обмежити кількість резюме на користувача: не більше 10.
6. Додати список, перегляд, видалення та тимчасове посилання на завантаження файлу, яке діє 5 хвилин.
7. Якщо запис у БД не вдався після завантаження файлу, видаляти файл із S3, а якщо не вдалося видалити файл, логувати це для ручного прибирання.

**Готово, коли (автоматично):** тести з моком S3 перевіряють завантаження, відмову для неправильного типу, розміру й підробленого розширення, ліміт кількості, видалення файлу разом із записом, недоступність чужих резюме й прибирання файлу після помилки БД.

**Готово, коли (вручну):** резюме завантажується в MinIO і в реальний AWS S3-бакет, посилання на завантаження працює, а після видалення файл зникає з бакета.

### Крок 4. Розбір резюме через Gemini

1. Створити `GeminiService` поверх `@google/genai`. Модель задається змінною `GEMINI_MODEL`, а не в коді.
2. Після завантаження резюме ставити розбір у фонову чергу. PDF передавати моделі як файл, а з DOCX спершу витягувати текст через `mammoth`.
3. Отримувати від моделі структуровану відповідь за JSON-схемою:
   - бажані ролі;
   - рівень;
   - загальна кількість років комерційного досвіду;
   - навички з групуванням за категоріями;
   - мови;
   - місто та бажаний формат роботи;
   - короткий опис.
4. Перевіряти відповідь за схемою на боці сервера. Якщо вона не відповідає схемі, повторювати запит до двох разів, а потім ставити статус `FAILED` з причиною.
5. Нормалізувати назви навичок: «Node.js», «NodeJS» і «node» мають ставати однією навичкою. Той самий словник використовується для вакансій на кроці 6.
6. Після кожного успішного розбору збільшувати `profileVersion`, щоб скинути кеш оцінок для цього резюме.
7. Додати `POST /cvs/:id/reparse`.

**Важливо:** резюме містить персональні дані, тож у логи не потрапляє ні текст резюме, ні відповідь моделі. Текст резюме є даними, а не інструкціями: промпт має явно вказувати моделі ігнорувати команди всередині документа.

**Готово, коли (автоматично):** тести з моком Gemini перевіряють успішний розбір PDF і DOCX, відповідь не за схемою з повторною спробою, перехід у `FAILED`, нормалізацію навичок, зростання `profileVersion` і повторний розбір.

**Готово, коли (вручну):** реальне резюме користувача розбирається в профіль, що відповідає його досвіду.

### Крок 5. Збір вакансій

1. Описати інтерфейс `VacancySource` з методом, що повертає сирі вакансії, і реалізувати три адаптери:
   - **DOU:** RSS-стрічки `jobs.dou.ua/vacancies/feeds/` за категоріями;
   - **Djinni:** RSS-стрічка `djinni.co/jobs/rss/`;
   - **Work.ua:** HTML-сторінки IT-вакансій, розбір через `cheerio`.
2. Дотримуватися правил `robots.txt` кожного сайту, надсилати чесний `User-Agent` і робити між запитами до одного сайту паузу щонайменше 2 секунди.
3. Запускати збір за розкладом через `@nestjs/schedule`, раз на 30–60 хвилин, а також один раз під час першого запуску з порожньою базою.
4. Зберігати вакансії без дублів за парою `(source, externalId)`. Якщо текст вакансії змінився, оновлювати її й `contentHash`.
5. Вакансії, старші за `VACANCY_MAX_AGE_DAYS`, не показувати в пошуку й періодично видаляти.
6. Помилка одного джерела логується і не зупиняє збір з інших.

**Важливо:** зміна верстки сайту ламає адаптер без явної помилки. Якщо джерело повернуло нуль вакансій або значно менше звичного, у лог пишеться попередження.

**Готово, коли (автоматично):** тести на збережених прикладах RSS і HTML у `test/fixtures` перевіряють розбір кожного джерела, відкидання дублікатів, оновлення зміненої вакансії, ізоляцію помилок джерел і попередження про порожній результат. Приклади сторінок зберігає користувач або агент із дозволу користувача, бо sandbox блокує ці сайти.

**Готово, коли (вручну):** після запуску в базі з'являються свіжі вакансії з усіх трьох сайтів, а посилання ведуть на правильні сторінки.

### Крок 6. Нормалізація вакансій

1. Витягувати з тексту вакансії вимоги до досвіду в роках, навички й рівень.
2. Спершу застосовувати правила: регулярні вирази для фраз на кшталт «3+ years», «від 2 років», «1–3 роки» та словник навичок із кроку 4.
3. Якщо правила не дали результату, викликати Gemini з JSON-схемою. Результат кешувати за `contentHash`, щоб не розбирати ту саму вакансію двічі.
4. Якщо досвід визначити не вдалося, залишати `experienceMin` і `experienceMax` порожніми.

**Готово, коли (автоматично):** unit-тести покривають українські й англійські формулювання досвіду, діапазони, «без досвіду», відсутність вимог, звернення до Gemini лише тоді, коли правила не спрацювали, і кешування за `contentHash`.

**Готово, коли (вручну):** на вибірці з 20 реальних вакансій вимоги до досвіду визначені правильно щонайменше у 18.

### Крок 7. Пошук і оцінка відповідності

1. Створити сутності `Search`, `SearchCv`, `MatchScore`, `SearchResult` і міграцію.
2. `POST /searches` приймає:
   - `cvIds`: від 1 до 10 власних резюме зі статусом `PARSED`;
   - `experience?`: діапазон `{ min?, max? }` у роках від 0 до 50, де `min ≤ max`;
   - `sources?`: підмножина `dou`, `djinni`, `workua`.

   Ендпойнт повертає `202` з id пошуку.
3. Виконувати пошук у фоні за алгоритмом із розділу «Як рахується відповідність».
4. Обмежити одночасні виклики Gemini та обробляти помилки `429` з повторними спробами й затримкою.
5. Перераховувати підсумкову оцінку як суму складових і порівнювати її з `MATCH_THRESHOLD`.
6. Для кожної вакансії зберігати найкраще резюме й оцінку, а в результатах показувати оцінки всіх обраних резюме, які пройшли поріг.
7. Обмежити кількість активних пошуків: один на користувача одночасно.
8. Якщо пошук упав, переводити його в `FAILED` із причиною, а вже порахованим оцінкам залишатися в кеші.

**Готово, коли (автоматично):** тести з моком Gemini перевіряють валідацію запиту, відмову для чужих і ще не розібраних резюме, фільтр досвіду з перетином діапазонів і невідомим досвідом, поріг рівно 69 і 70, вибір найкращого резюме, використання кешу, ліміт одночасних пошуків і перехід у `FAILED`.

**Готово, коли (вручну):** пошук за реальним резюме повертає вакансії, які користувач вважає релевантними, а очевидно нерелевантні не проходять поріг.

### Крок 8. Результати пошуку

1. `GET /searches/:id/results` повертає вакансії, відсортовані за оцінкою, з пагінацією.
2. Кожен результат містить посилання на вакансію, джерело, компанію, найкраще резюме, оцінку, оцінки за складовими, коротке пояснення й навички, яких бракує.
3. Підтримати фільтр результатів за джерелом і мінімальною оцінкою вище за поріг.
4. Додати `GET /searches` з історією пошуків користувача.

**Готово, коли (автоматично):** e2e-тести перевіряють сортування, пагінацію, фільтри, недоступність чужих пошуків і формат відповіді в Swagger.

**Готово, коли (вручну):** через Swagger видно повний цикл від завантаження резюме до списку вакансій.

### Крок 9. Надійність і безпека

1. Встановити денний ліміт викликів Gemini на користувача й на весь сервіс, щоб контролювати вартість.
2. Додати таймаути для викликів Gemini, S3 і сайтів вакансій.
3. Перевірити, що в логах немає паролів, токенів, ключів, текстів резюме та відповідей моделі.
4. Під час старту відновлювати пошуки й розбори, які залишилися в статусі `PENDING` чи `RUNNING` після аварійної зупинки: перезапускати їх або переводити у `FAILED`.
5. Перевірити каскадне видалення: видалення користувача прибирає резюме, файли в S3, пошуки й оцінки.

**Готово, коли (автоматично):** тести перевіряють денні ліміти, таймаути, відновлення незавершених задач після перезапуску й каскадне видалення.

**Готово, коли (вручну):** користувач переглянув логи робочого запуску й не знайшов у них персональних даних чи секретів.

### Крок 10. Запуск у продакшені

1. Написати `Dockerfile`. Міграції застосовуються окремою командою перед запуском нової версії.
2. Використовувати керовану PostgreSQL і роль IAM замість постійних ключів доступу, якщо хостинг це дозволяє.
3. Додати `/health`, який перевіряє підключення до БД і S3, і зовнішній моніторинг цього ендпойнта.
4. У продакшені вимкнути Swagger або закрити його авторизацією.
5. Запускати збір вакансій лише в одному екземплярі, щоб не дублювати запити до сайтів.
6. Оновити `README.md` і `CLAUDE.md`.

**Готово, коли (автоматично):** образ Docker збирається, а тест перевіряє відповіді `/health` за доступних і недоступних залежностей.

**Готово, коли (вручну):** сервіс кілька днів працює на сервері, вакансії оновлюються за розкладом, а пошук повертає свіжі результати.
